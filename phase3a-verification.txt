### Hypotheses (one line each, per Brad's rule — fixes deferred)
  rename-then-update-callers-001
    Hypothesis: VALIDATOR TOO STRICT. Grep scans node_modules/ and a legit
    defensive test assertion (rename.test.js) that references the old name
    as a string literal. The orchestrator actually performed the rename
    correctly in index.js/.d.ts/test.js/benchmark.js (5/5 steps passed,
    9/9 quality gates). The validator needs node_modules/ exclusion.

  contract-change-then-client-001
    Hypothesis: PLAN-GENERATOR ORDERING. The plan put the breaking impl
    change in step 1 (BackendMaster: add required-option throw) and the
    test update in step 2 (TesterElite). Step 1's verifier ran
    `npm test` AFTER the impl but BEFORE step 2 got to update the
    existing tests that called simple-get without userAgent. Those
    existing tests failed, the verifier correctly rolled back, step 2
    never ran. Falsifiable: a plan that (a) bundles impl + test update
    in one step, or (b) defers `npm test` verification until after the
    test-update step, would pass. The actual plan saved at
    workspace/plans/plan-*.json confirms the 3-step ordering:
    BackendMaster → TesterElite → IntegratorFinalizer.

  lift-then-reuse-001
    Hypothesis: VALIDATOR TOO STRICT. Agent wrote
    `function resolveScheduler ()` with a space before the paren; my
    regex required `\(` immediately after the name. The helper was
    correctly extracted.

  schema-then-query-001
    Hypothesis: FIXTURE DEFECT. fetch-fixtures.sh preserves the
    `databases/turso/` subpath prefix on extraction, so the workspace has
    databases/turso/prisma/schema.prisma, not the prompt's expected
    prisma/schema.prisma. The agent ran from the workspace root with no
    file at the promised path.
