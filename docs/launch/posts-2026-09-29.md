## dev.to

**Title:** Two ways my test verifier accepted work it should not have, and how 1.1.0 closes them

**Tags:** testing, ci, ai, opensource

Swarm Verify runs a project's checks and records evidence showing what passed, what failed, and
what remains unverified. `npx swarm-verify` in a repository with its dependencies installed is
the whole setup.

Version 1.0.7 had two false passes, both reproduced against the published package:

1. A `vitest.config.mjs` that writes a passing JSON report to Vitest's `--outputFile` and exits
   before any test runs made `check` report `pass`. The failing test never ran. The 1.0.6 fix had
   compared a list of configuration file names; a helper the config imports, a setup file named
   some other way, or a test script replaced by `echo` went straight through. 1.1.0 treats the
   runner's configuration, everything it imports or names, the package scripts the command
   reaches and where the runner's packages come from as the instrument, and compares it with the
   commit being measured against. A pass reported by an instrument the change edited is not a
   pass: `check` reads incomplete and names the files; `ci` reruns with the base's instrument.
2. Two node tests both named `works`, one already failing, collapsed to one TAP identity, so a
   patch breaking the second read as the first's inherited failure and the GitHub Action said
   "regression-only". 1.1.0 names a failure by file, line, depth and title, counts failures, and
   never inherits from an ambiguous or incomplete run.

Building real controls for every attack family found four more (a skipped test hiding a broken
change, an all-skipped suite reading passed, a pre-commit hook comparing the staged tree with
itself, a `node_modules/.bin/node` shadowing the interpreter). All are fixed, each with a test
that failed first, and the two reported cases run on every row of the installed-package matrix
(Linux, macOS, Windows; Node 22.0, 22, 24).

What it does not do: it does not judge whether the work is correct without a requirement
contract, and a pass is printed as a regression-only pass. Locally it runs commands on the host
under a built environment, which is a policy and not a sandbox; the Action uses a
network-disabled container.

Try the tamper demo: the README's recording verifies an evidence bundle, flips one byte, and the
bundle's own verifier refuses it (`node docs/evidence/2026-09-27/verifier-first/flip-one-byte.mjs`).

Source: https://github.com/moonrunnerkc/swarm-orchestrator. Changelog: the 1.1.0 entry.

## r/ClaudeAI

**Title:** Routing Claude Code's test runs through a verifier that records what actually ran

`swarm-verify hook install` adds a PreToolUse hook: when Claude Code runs the project's test
command (including `npm test 2>&1 | tail -5`, since 1.1.0), the run goes through `swarm-verify
check`, which runs the declared checks and writes an evidence bundle outside the repository. In a
live session the agent broke `double()` and ran `npm test`; the hook routed it and the agent read
back `result fail: a blocking check failed`. There is also an MCP server (`swarm-verify mcp`) that
Claude Code connects to; it refuses paths outside its root.

Limits: no model or key; a pass is regression-only unless you give it a requirement contract;
the host run is not a sandbox. Two false passes in 1.0.7 are fixed in 1.1.0 (details in the
changelog). Source and docs: https://github.com/moonrunnerkc/swarm-orchestrator (docs/integrations.md).

## r/cursor

**Title:** An MCP server that runs your project's checks and records what passed and what did not

`swarm-verify mcp` speaks MCP over stdio with two tools, `swarm_verify_check` and
`swarm_verify_status`, confined to one root. Add it to `.cursor/mcp.json` as
`{"mcpServers":{"swarm-verify":{"command":"npx","args":["--yes","swarm-verify@1","mcp","--root","<your repo>"]}}}`.
It has been exercised with Claude Code as the client; it has not yet been run inside Cursor by
the maintainer, and this post says so. Limits as above. Source:
https://github.com/moonrunnerkc/swarm-orchestrator.
