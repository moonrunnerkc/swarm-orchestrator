# 0004. Bundle consistency and bundle authenticity are separate claims

**Status:** accepted

## Context

A bundle carries the public key its own signature verifies against. So the check it can make
about itself is "unchanged since written". Anyone who edits a bundle, rehashes it, signs the new
chain head with a key of their own and ships that key in the manifest gets a signature that
verifies perfectly. That was being read as authenticity.

## Decision

Three claims, told apart wherever a verdict is reported:

1. **Consistency**: the chain rehashes and the signature over its head verifies. A bundle can
   prove this about itself.
2. **Authenticity**: it was made by someone in particular. A bundle cannot prove this about
   itself, so the expected identities come from the caller: `swarm verify <dir> --signer <fp>`.
3. **Execution trust**: whether the machine that produced it was sound. Nothing here establishes
   this, and the output says so rather than leaving it to be assumed.

Named and matching is `trusted`. Named and not matching is `untrusted`, with both fingerprints in
the message. A signature that does not verify is `invalid`, which is a different finding. With no
signer named the answer is `untrusted`, never `trusted`. An ephemeral key is never trusted
whatever the policy names, because it was generated by the run it vouches for.

A fingerprint is SHA-256 over the SPKI DER the manifest carries.

## Consequences

`swarm verify` exits non-zero unless a named signer matched, which makes "verified" mean
something in a script.

## What this does not buy

A trusted signer says the bundle came from a key someone trusts. It says nothing about whether
that key's holder was honest, whether their machine was compromised, or whether the evidence
inside describes what actually happened on some other machine.
