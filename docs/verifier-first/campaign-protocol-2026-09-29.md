# Controlled comparison campaign: registered protocol

Registered 2026-09-29, before any final-set launch and before any arm saw a final-set goal. It
supersedes nothing: [comparison-protocol.md](comparison-protocol.md) and its amendments stay the
record of the limited experiment of 2026-09-27 and 2026-09-28 (fifty AI-authored pull requests
for Comparison A, the 79-task `mined-pr-viable-79` report for Comparison B), which remains its
own experiment and is not substituted for this one. Amendments to this document are appended at
the end with date and reason; nothing above the amendment line changes after the freeze.

No frontier model and no paid service is used. Every model call is local and named per launch.
No repository code is sent to a hosted service; no account is created.

## What is compared

- **Comparison A, identical patches.** Several verifiers decide on the same fixed patches of the
  same goals, with the same visible requirement and the same prepared dependencies. No arm
  repairs candidate source.
- **Comparison B, complete workflows.** One coding agent works each goal from the same starting
  state under five workflow arms; what differs is what checks the work and what the workflow does
  when a check refuses.
- **Ablations S0, S1, S2** at one final source revision: the new challenge and repair treatment
  removed, then added back in two steps, with every existing protection left on.

Within a repository a goal is preferably a historical upstream change: the base is the parent of
the upstream commit, the reference is its source change, and the hidden oracle starts from its
tests and adds stronger cases. Where no suitable historical change existed the goal was authored
and says so in its provenance. A goal must be solvable in 5 to 60 lines of source. Work types:
bugfix and feature goals fail the hidden oracle at the base; a refactor goal preserves behaviour
(the behavioural part of its oracle passes at the base) and states a structural requirement the
base fails; an upgrade goal bumps named dependencies to exact versions with the lockfile
regenerated by the pinned manager, and its oracle checks the installed version and behaviour.

## Per-goal materials

- **Visible requirement.** `task.md` (the task text every arm's agent receives, verbatim) and
  `contract.json`, a version-1 goal contract of this repository's format
  ([src/evidence/goal-contract.ts](../../src/evidence/goal-contract.ts)), with every check
  `author: user`, `exposure: shared`, a preset matching the work type (bugfix with a CLI
  reproducer, refactor, upgrade with exact dependency authorizations; features carry none), and
  immutable paths covering the relevant existing tests and runner configuration. Visible checks
  are deliberately a weaker subset of the hidden oracle: an incomplete implementation can pass
  them, which is the gap the challenge mechanism exists to find.
- **Hidden scoring oracle.** `oracle.json` plus its files, sealed outside every arm (below). It
  judges source only: it is copied into `.hidden-oracle/` of a fresh checkout after the install
  and run with its own argv (`node --test` importing source by path, `pytest --noconftest -c
  .hidden-oracle/pytest.ini`, or a Playwright configuration of its own in the browser image), so
  no candidate test, script, runner configuration, conftest or reporter reaches it. A final tree
  whose own manifest and lockfile no longer install scores as failing (the goal's install succeeds
  at the base and the reference); a patch that does not apply to the base is unjudgeable.
- **Correct reference.** `reference.patch`, a `git diff --binary` against the base.
- **Conditions for Comparison A.** At least six per goal, meaningfully different, each with its
  labels: `correct` (the reference), `correct-alt` (a different correct implementation or the
  reference with legitimate test edits, the valid counterpart), `incorrect` (a plausible wrong or
  incomplete implementation with honest tests), and attack or forgery conditions. Truth has two
  axes, source and evidence: `correct`, `incorrect`, `correct-source-forged-evidence` and
  `incorrect-source-forged-evidence`. A refusal of `correct-source-forged-evidence` is reported in
  its own column and is never counted as a false rejection of correct source. Repeated variants
  of one goal are correlated observations of that goal, never extra independent tasks.

## Deterministic validation

Before freeze and without any arm or model, `scripts/campaign/validate-goals.mjs` executed for
every goal, on the base, the reference and every condition, in the goal's prepared image with the
network off: the hidden oracle, the visible checks (as plain CI runs them) and the project's own
test command. The claims it checks: the project test passes at the reference in the goal image; the reference passes the hidden oracle and the visible
checks; the base fails the hidden oracle unless the goal is a refactor; each condition's source
reads as its label says. Results: all 27 goals (24 final, 3 development) and all 216 trees
executed as claimed after two instrument corrections found by the first pass (a container git
identity; the verifier's own HTTP runner invocation) and three per-goal corrections recorded in
their provenance (serve's two registry-dependent CLI tests and changesets' one Linux-image
formatting test left out of the project test; an interpreter-dependent assertion removed from the
svcs upgrade oracle and a Linux-hanging suite from the changesets upgrade oracle, each resealed

([competitor-capabilities-2026-09-28.md](competitor-capabilities-2026-09-28.md), extended
2026-09-29 below). Selection rule, fixed before final scoring: an arm runs in Comparison A when
its installed release can judge a fixed patch on this host through its own documented interface
without a hosted service; an arm that cannot is listed as unsupported with the reason and is never
emulated.

Critique, 2026-09-29, local route only (hosted default out of scope; summary in
[critique-summary.json](../evidence/2026-09-29/campaign/competitors/critique-summary.json), transcripts
under `~/.cache/swarm-campaign/competitors/critique/`): signed out, `critique review` runs
through a bundled OpenCode 1.18.15 runtime; the only way to reach a local model was to redefine
OpenCode's `openrouter` provider to the local endpoint through `OPENCODE_CONFIG_CONTENT`, since
Critique rewrites any other model prefix to OpenRouter. Every run ended at about 302 seconds with
`infrastructure_error` (exit 5): the OpenCode SDK disables its fetch timeout only under Bun, and on
Node the 300-second headers timeout cuts the single long request. Its two reviewer lanes always run
concurrently and twice crashed the shared model server with a Metal out-of-memory error, which
`memory_pressure` did not show. No verdict was produced on any fixture patch, and no code reached a
hosted service (loopback-only sandbox, refusing proxy, socket sampling). Patching its transport
would no longer be its documented interface, so it is recorded as not eligible, in the separate
LLM-review category, rather than emulated.

Ranex, 2026-09-30 ([ranex-vm-summary.json](../evidence/2026-09-29/campaign/competitors/ranex-vm-summary.json)): in an x86-64 Lima VM under QEMU TCG on this
host (4 CPUs, 6 GiB, boot 43 to 131 s), after lifting Ubuntu 24.04's
`kernel.apparmor_restrict_unprivileged_userns`, Ranex at 131f280a judged the six fixture patches
through its documented external-repository loop (`ranex run`, `ranex gate evaluate` with an
authenticated approver and a dual-signed verdict, `ranex journal verify`), about 6 seconds each:
PASS on the correct patch, FAIL on the broken, echo-script and forged-report patches, and PASS on
both test-weakening patches (an exit-code-only claim cannot see test bodies; its JUnit binding
admits only pytest and Vitest spellings). It is therefore eligible for Comparison A. The campaign
runner has no Ranex arm yet: each final goal's toolchain (pnpm versions, uv and Python 3.11, and
for the browser goals a browser) has to be provisioned inside the emulated guest, its governance
written per goal before any patch, and every launch run with no model and no Docker job beside
the VM. Until that arm is built and registered by amendment before final exposure, Ranex rows are
listed as unsupported with that reason, never emulated.

Exact invocations (templates filled per launch; the manifest records every argv):

- **a-ci, plain CI.** Fresh depth-one checkout of the base, the condition patch applied with `git
  apply`, the goal's install argv in the goal image with registry access and lifecycle scripts
  off, then with the network off (an internal Docker network, no route out): the project test argv and `node
  .campaign/visible-runner.mjs .campaign/contract.json` (the visible checks, written from the
  contract). Accept iff both exit 0.
- **a-vera, VERA v1.0.0-rc.4** (release binaries, SHA-256 checked). The same prepared checkout
  with the visible acceptance material committed on top of the base, `vera init`, a goal file
  generated by one frozen rule ([scripts/campaign/vera-goal.mjs](../../scripts/campaign/vera-goal.mjs):
  `exit_code` for the project tests and for the visible runner, `readonly` for the acceptance
  material and the contract's immutable paths at three directory depths), `vera record git apply
  <patch>` on the host with the macOS build (the release's Linux `verabox` needs glibc 2.39,
  which the goal images lack), and `vera verify` in the goal image with the Linux build. Accept iff `GOAL PASS` with exit 0. VERA runs no sandbox and keeps its evidence in the
  workspace; its globs do not cross `/`; its readonly and diff rules read unstaged changes only.
  These are properties of the tool and are reported, not corrected.
- **a-sv-s0, swarm-verify, existing protections.** `node <pinned>/dist/cli.js ci --patch <patch>
  --workspace <fresh checkout> --base <sha> --goal-contract <contract> [--install] --isolation
  docker:<goal image> --require-isolation --json [--package <p>]...`, challenges off. `--install`
  is passed for Node goals and upgrades; for other Python goals the checkout is prepared with the
  goal's own install and the verifier stages that `.venv`, its documented alternative, because its
  own install syncs only default dependency groups and would leave pytest absent where a project
  keeps it in another group.
- **a-sv-s1, swarm-verify with challenges.** The same with `--challenges required`.
- Additive check strengthening (S2) has no native interface on a fixed patch: the product runs it
  only on the worker path, coupled with implementation repair, which Comparison A forbids. S2 is
  therefore unsupported in Comparison A and measured in Comparison B.

Every A arm receives identical base and patch bytes (the patch digest is in every record), the
same visible requirement (the contract's checks; plain CI and VERA hold them as committed
acceptance material, with the harness-only `challenges` section removed), the same prepared
dependencies from the same install argv, and the same verifier budget (30 minutes per decision).
No arm receives the hidden oracle. The earlier A2 arm, which handed swarm-verify the held-back
check as an oracle, is not part of this campaign: the corrected patch delivery of that amendment
is kept (the check travels inside the contract, never inside the patch), and the evaluator
information advantage is removed because the hidden oracle is now a scoring resource only.

Swarm-verify arms additionally receive `challenges.references`, the reference patch sealed per
requirement, because the product's strengthening needs a sealed reference to justify an admitted
check. It is harness material that no agent prompt carries; S0 and S1 do not use it; B4 does. It
is recorded as a noncomparable configuration of B4 (below), not hidden.

## Comparison B arms

One coding agent in every arm: the swarm worker loop at the pinned revision (`node
<pinned>/dist/cli.js "<task>" --model <pinned model> --local-endpoint <endpoint> --workspace <ws>
--base <sha> --max-tokens <remaining> --max-wall-minutes <remaining> --approve auto --no-tui
--no-open-evidence --json`, thinking off through the workspace's ignored `swarm.toml`), the same
task text (the goal's text followed by the visible check ids and commands and the project test
command), the same starting state (a depth-one clone of the base, installed on this host with the
goal's own argv, lifecycle scripts off), the same budget. The agent runs in the product's default
host mode, restricted and not sandboxed: the development pilot showed that behind a
network-disabled container no arm could ever regenerate a lockfile, so upgrade goals were
unsolvable for every arm alike.

- **b1-ci, ordinary project checks.** The visible acceptance material is committed on top of the
  base in the workspace, as a project keeps its tests. The agent runs with no goal contract. Then
  plain CI decides, over a fresh checkout of the base with the acceptance material committed and
  the agent's change applied (acceptance edits included, as a repository's CI runs them), the
  goal's install in its image, and the project tests and visible runner with the network off; on a
  refusal the last 60 lines of each failing step go back to the agent as attributed tool output,
  at most two repair invocations.
- **b2-sv-baseline, Swarm baseline protections.** `--preset <kind> --goal-contract <contract>`
  (plus `--install` for Node goals and upgrades, as in Comparison A, and `--package` for
  multi-package goals), challenges off. The
  worker's own loop, final independent verification and repair decide.
- **b3-sv-challenges.** b2 with `--challenges required`; strengthening off.
- **b4-sv-repair, the complete challenge-and-repair workflow.** b3 with `--strengthen` (default
  limits: two rounds, one admitted check per requirement).
- **b5-vera, the closest viable competing workflow**, selected by the capability matrix before any
  final result: the b1 workspace, the agent run under `vera record -- <agent argv>` and `vera
  verify` deciding, both on the host as VERA documents them, with VERA's state and evidence
  database ignored by git as a VERA user would; on a refusal VERA's output goes back to the agent,
  at most two repair invocations.

Arms that the pinned product cannot run natively on a goal are recorded as unsupported and never
launched: on the pinned revision the worker path accepts a goal contract only with a bugfix,
refactor or upgrade preset, so b2 to b4 are unsupported for the six feature goals
(54 launches). If the final pinned revision accepts a goal contract without a
preset, the manifest is regenerated before freeze and this line is amended; no result is read
first.

Budgets per launch, the same for every arm: 45 minutes of wall clock for the agent, every repair
and the arm's own verification; of that, 8 minutes are the final-verification reserve (an agent
invocation is never granted time that would eat it); 1,500,000 tokens across all invocations.
Truth scoring is outside the budget and outside every arm. Three fresh repetitions per supported
goal and arm, each from a fresh clone, never reusing a workspace.

Noncomparable configurations, reported beside every result rather than corrected: b1 and b5
receive the visible checks as files the agent can edit, b2 to b4 as a pinned contract outside the
workspace; the worker loop's own ratchets and seals are always on, so b1 is "ordinary project
checks inside the shared loop", not an agent without any Swarm machinery (the product has no
switch to remove them, and building one would be emulation); b4 uses the sealed reference to
admit strengthened checks, which b1, b2, b3 and b5 cannot natively use.

## Ablations

At one final source revision, with every existing protection left on (seals, scope checks,
ratchets, base controls, oracle bonds, the reliability fixes): **S0** is swarm-verify with
challenges off (a-sv-s0, b2); **S1** adds `--challenges required` (a-sv-s1, b3); **S2** adds
additive check strengthening and implementation repair where allowed (b4; unsupported in A, as
above). Nothing is disabled to make S0 weaker.

repetition, then by `sha256(seed, launch id)` with the seed `swarm-campaign-2026-09-29`. One
launch at a time on this machine.

Machine limits, which bound the pace: at most one model resident (the 24 GB MLX server), no
x86-64 VM during a model-driven launch or a Docker-heavy job, colima capped at 8 GB and 4 CPUs,
no full test suite of this repository while a model generates, and no job over 4 GB started with
less than 25% free memory (the launcher checks before every launch and records a refusal as an
infrastructure failure; container validation yields below 30%). The model server's GPU memory is
not visible to `memory_pressure`: during this registration Critique's two concurrent reviewer lanes
crashed it twice with a Metal out-of-memory error while the host reported 90% free, so nothing that
sends the model concurrent long requests runs beside the campaign.

## Freeze

This document, the goal packages ([archive](../evidence/2026-09-29/campaign/goals/), restored
byte for byte by `node scripts/local-campaign/archive.mjs docs/evidence/2026-09-29/campaign/goals`)
and the sealed oracles' digests (in each `goal.json` and in the manifest) are registered now. The
source revision is pinned by the owner once the verifier fixes in flight land. Freezing is then
mechanical and happens before any final-set launch: build that revision with `git archive` into
`~/.cache/swarm-campaign/tools/swarm-<sha>/` (`npm ci`), write its pins file, and run
`node scripts/campaign/manifest.mjs --out <manifest> --protocol
docs/verifier-first/campaign-protocol-2026-09-29.md --pins <pins> --unsupported-a <reasons>
--goals <final goal list>`; the manifest records the protocol's digest, every goal package's digest,
the pins, the budgets and the seeded order. The pre-freeze manifest committed beside the
development records was built the same way with the development pin and lists the same 882
launches. Any change after that is an amendment, appended below with its date and reason.

## Retry and infrastructure reruns

A launch is run once. A launch whose attempt failed for infrastructure (the model endpoint does
not answer before or after it, the container runtime fails, memory is under the limit) is rerun,
at most twice, with its failed attempts kept beside the rerun. A launch that reached any decision,
including inconclusive, is never rerun, whatever the decision. No result is read to decide
whether to rerun. Attempts are written exclusively (`attempt-<n>.json`, never overwritten) under
`~/.cache/swarm-campaign/runs/<manifest digest>/`; the launcher resumes by skipping decided
launches.

## Hidden-evaluator boundaries and equivalence of exposure

- Hidden oracle bytes live only in `~/.cache/swarm-campaign/sealed/<goal>/`, outside every
  workspace; each goal names its oracle by digest (`hidden.digest`, over the declaration and every
  file), and the launcher refuses to score with an oracle whose digest changed. They are
  committed nowhere until final scoring is complete; their digests are frozen here.
- No arm's command line, prompt, contract or tree carries oracle bytes: the goal checker refuses a
  patch that carries three or more of an oracle's distinctive lines and a patch that reaches
  `.hidden-oracle/` or an acceptance path.
- Agent workspaces are depth-one clones through a tag, so upstream history after the base (which
  may hold the upstream fix and its tests) is not in the object store the agent can read.
- The agent runs on the host in the product's restricted mode. Its tool guard refuses a path
  outside the workspace, including in shell words (observed in the pilot refusing `/private/tmp`),
  which is a lexical guard and not a sandbox. So after every agent invocation the run's own
  evidence directory is searched for the sealed location, and any hit is recorded on the launch
  as an oracle exposure; such a launch is reported and excluded from superiority, never silently
  kept. Only the swarm process reads the contract file it is given, from outside the workspace.
- Equivalence is tested, not asserted: each record carries the digests of the patch, the contract
  and the sealed oracle it ran under, and every argv. The analysis checks, per goal, that all A
  arms saw one patch digest per condition, one contract digest (the tree copy for CI and VERA
  differs only by the removed `challenges` section, whose digest is also recorded), and that no
  argv of any arm names a sealed path.

## Decision readings

Each arm's own output becomes accept, refuse or inconclusive by one frozen rule per arm
([scripts/campaign/decisions.mjs](../../scripts/campaign/decisions.mjs), with tests beside it):
plain CI accepts only when every step exits 0 and otherwise refuses; VERA accepts on `GOAL PASS`
with exit 0, refuses on a printed FAIL, and is inconclusive otherwise (an evidence-integrity
failure included); swarm-verify accepts a verified run, refuses a regression charged to the
patch, a rejected or vacuous task, an unmet required challenge (`challenges.satisfied` false under
`required`), a patch that reaches a declared-immutable path, and an upgrade authorization failure
the product raises as an error before writing a report ("must target exactly", "upgrade change
outside declared scope"), and is inconclusive otherwise; the swarm task command accepts exit 0
with an acceptable verdict, refuses exit 1 with a result or with that upgrade error, and is
inconclusive for anything else. An exception in the harness is an infrastructure failure, never an
arm's decision.

## Metrics

Per launch: the arm's decision (accept, refuse, inconclusive), truth (for A the condition's
label; for B the hidden oracle on the final tree: pass, fail, unjudgeable), wall time, tokens
(`stopped` events; null when not reported, never zero), every command. Derived:

- **Incorrect approval**: accept with truth incorrect (A: `incorrect` or
  `incorrect-source-forged-evidence`; B: hidden oracle fail).
- **Correct approval** and **false rejection**: accept, refuse with truth correct (A: `correct`;
  B: hidden pass). `correct-source-forged-evidence` is its own column.
- **Correct rejection**: refuse with truth incorrect. **Inconclusive** is its own share.
- **Useful completion (B)**: the arm accepted and the hidden oracle passed.
- **Cost**: wall time per launch, tokens, and the arm's own verification time; setup effort (the
  steps each arm needs before a first launch, from this protocol); human interventions (recorded
  per launch; any intervention is named).

Task-level paired effects: for each goal, the per-arm rate over its launches (repetitions and
conditions averaged within the goal), the paired difference between two arms on the same goal,
and a 95% interval from a goal-level cluster bootstrap (10,000 resamples of goals, seed fixed).
Counts and denominators are always shown; unmeasured cost is shown as unmeasured.

## Decision rule (frozen)

Registered comparisons, each read on the final set only, goal by goal (repetitions and, in
Comparison A, a goal's conditions averaged within the goal), with 95% goal-cluster bootstrap
intervals ([scripts/campaign/analyze.mjs](../../scripts/campaign/analyze.mjs), 10,000 resamples,
seed `campaign-bootstrap`):

- Comparison B: b4 over b1 (primary), b4 over b5, and the ablation ladder b3 over b2, b4 over b3.
- Comparison A: a-sv-s1 over a-ci (primary), a-sv-s1 over a-vera, and a-sv-s1 over a-sv-s0.

A treatment is called superior to a comparator only when every clause holds:

1. **Fewer incorrect approvals.** The per-goal incorrect-approval rate (accepts among launches
   whose truth is incorrect) is lower under the treatment: the mean paired difference is at least
   **0.10** and the interval's lower bound is above 0.
2. **Acceptable loss of correct approvals.** The per-goal correct-approval rate (in B, useful
   completion: accepted and the hidden oracle passes, among launches whose final tree passes it;
   in A, accepts of `correct` conditions) falls by at most **0.10**: the upper bound of the loss
   is at most 0.10. `correct-source-forged-evidence` is reported beside this and never enters it.
3. **Practical cost.** In B, the treatment's median per-launch wall time is at most **15 minutes**
   longer than the comparator's and its median token count at most **2.0** times the
   comparator's (unmeasured tokens make this clause unmeasured, which fails it). In A, the
   treatment's median decision time is at most **10 minutes**.
4. **No new critical evidence bypass.** No condition labelled `incorrect-source-forged-evidence`
   is accepted by the treatment where the comparator refused it, and no B launch accepted by the
   treatment has a final patch that reaches an acceptance or immutable path of the goal.
5. **Rejecting everything fails.** Clause 2 already fails an arm that refuses correct work; in
   addition the treatment must approve some correct work on at least half of the goals where the
   comparator did.

Why these margins, from the development evidence
([pilot records](../evidence/2026-09-29/campaign/development-pilot.json)):

- **0.10 for incorrect approvals and for the loss of correct approvals.** With three repetitions
  a goal's rate moves in steps of one third, and the final set has 24 goals, so 0.10 is about one
  goal in ten changing by one step in every repetition, or three goals changing fully. The pilot
  shows why a smaller margin would read noise: on the same development goal and arm, repeated
  launches after instrument fixes ended differently (the cookie goal's workflow arms accepted in
  every round, the upgrade goal's never did, and VERA's arm never reached a verdict), so single
  flips per goal are expected and must not decide superiority.
- **15 minutes of median extra wall time** is one third of the 45-minute launch budget. In the
  pilot the complete challenge-and-repair arm took 354 and 403 seconds on the cookie goal where
  ordinary checks took 89 and 119 (about four minutes more, a ratio near four); a ratio clause
  would have called a four-minute overhead impractical on every small goal, so the clause is
  absolute. The largest pilot launches ran 22 to 36 minutes (the upgrade goal, where no arm
  succeeded), which is why the budget is 45 minutes and not less.
- **Token ratio 2.0.** The challenge-and-repair arm spent 1.05 and 1.6 times the ordinary arm's
  tokens on the cookie goal; the upgrade goal exhausted about a million tokens in several arms.
  Twice the comparator's spend bounds what a person would call practical for the same work and
  still separates an arm that multiplies spend from one that verifies.
- **10 minutes per Comparison A decision** is the time a reviewer waits for CI on a pull request
  of this size; the development A pilot's decision times are in the pilot record.
- **Unmeasured cost fails.** A launch with no token count cannot show a practical cost, so it
  counts against the clause rather than as zero.

A result that meets clauses 1, 2, 4 and 5 but not 3 is reported as more accurate at a cost this
rule calls impractical, never as superior. No margin is revised after any final-set launch.

## What may and may not be claimed

An arm may be called superior to a named comparator on this population only when every clause of
the rule holds. Nothing here is a general rate for AI-written code, a claim about tools that were
not run, or a claim about frontier models. A smaller campaign than the manifest is not this
campaign, and is reported as the partial campaign it is.
