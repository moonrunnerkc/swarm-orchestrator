## Per-test judgment

- Five runners are recognized, as specified: pytest, jest, vitest, mocha and go test. `node --test` is not one of them, although every demo and the README's example use it; those stay judged by exit code, and their verdicts now say so. Adding Node's junit reporter would be one more line in the table and is left as an open choice rather than taken, since the five were the specification.
- A runner is recognized in the command itself or in the one `package.json` script an `npm`, `pnpm`, `yarn` or `bun run` command names, read from the base. A chained, piped or redirected command, a script that calls another script, `bun test` (bun's own runner) and go test behind a script are not recognized: there is no one place a flag belongs. The flags pass through `--` for npm only, since pnpm, yarn and bun forward trailing arguments themselves.
- vitest keeps its default reporter beside the JSON one, so a failure still prints what the agent acts on. mocha takes one reporter, so a mocha check prints nothing with the change; its failing ids are in the verdict's reasons. go test's events go to the report file, so a go check's printed output is its standard error.
- Test ids are the runner's own: `classname::name` from junit, `file::full title` for the JavaScript runners with the file relative to the checkout, `package::Test` for go. A test reported twice counts at its worst. A jest or vitest file that fails to load, and a go package that fails with no test reported, stand in as one failing entry for the tests they hold.
- Skipped is read as not passing: a test that passed at base and is skipped with the change regressed, since skipping is how a change silences a test; one that was skipped at base and fails with the change is newly failing. A test absent at base that fails with the change blocks too: the verdict says the change broke nothing its tests can see, and a failing test it added is something they see.
- A deletion is allowed only when `[protect] allow` includes `tests` and the test lived in a file the change edited. Where that is depends on the runner: a path for jest, vitest and mocha, a dotted module turned into a path for pytest's junit (whose default family names no file), the package directory for go.
- A check also fails when its command exits nonzero with the change and zero at base though every test in its report passes (a coverage threshold, a crash after the report was written): the per-test rule says nothing about that and passing it would hide a real failure.
- A recognized check whose command could not run, at either commit, is unmeasured with the reason, where the exit-code path still fails a check that could not run with the change. The specification reserves unmeasured for that case; the exit-code path is unchanged so that checks without a recognized runner behave as they did.
- The judge is loaded into declared test checks at both commits, not only held-out ones, so a patched assertion helper shows in the check the change was asked to pass. A finding the base run shared does not block (a runner that kills its workers at exit leaves the same "exited before the judge could check them" at both); a finding naming what the change patched blocks unless the base named the same.
- The runner's report is written by the code under test's processes, as its exit code always was: a change that forges the report is out of reach in the same way, and docs/verifying.md now names the report among what the judge cannot protect.
- The base run's reports are stored in the existing cache entry, keyed as before: the environment digest in the key already holds each check's command. A cache file written before this change has no reports, fails its schema and is run again.
- Each kind of id in the predicate is capped at 100 with the true totals in `counts`: a change that breaks an import can fail thousands of tests, and the statement is signed and carried with the patch.
- The mutation pass reads the mutant's report against the change's: killed means a test passing with the change does not pass under the mutant, or the mutant kept the report from being written. Comparing exit codes instead would read every pre-existing failure as a kill.
- A check whose report has no test passing with the change, and nothing that blocks, is unmeasured, a third case beside the two the specification names (could not run, could not parse). Without it the replay below read as a measured pass with nothing passing: pytest had stopped at collection at both commits. Unmeasured never counts as a pass, and a verdict that cannot tell the change from no change is not a pass.
- pytest gets `--continue-on-collection-errors`. Without it one module that fails to import stops every test from running; with it that module is one failing entry, pre-existing when it fails at base too and newly failing when the change broke it, while its tests that ran at base read as deleted and fail the check. jest, vitest, mocha and go test already carry on past a file or package that fails to load.
- Held-out checks keep the exit-code judgment for now.
- Sandboxed check execution stays in docs/FOLLOW-UPS.md. Running every check in a container or VM brings back the container runtime and daemon the rebuild removed, which changes what the product depends on to install and run, and nothing in per-test judgment or the fix loop needs it: both read reports and verdicts that the unsandboxed run already produces.

## 2026-10-31: requirement completion

- R1 is always the user's task verbatim, so a model cannot finish by dropping or rewording what was asked; its kind defaults to `other` until the model proposes one, which keeps an unmapped R1 unverified rather than inferring evidence for it.
- The model proposes the record in a fenced `requirements` block, the same one-block-per-reply protocol as commands; it may carry the completion marker beside it. Nothing infers a mapping from which tests happened to pass.
- A completion repeated on the same patch and record digests stops the loop (`no-progress`) instead of verifying again: the findings would be identical.
- Final verification reuses a held result only when both the patch digest and the record digest match; anything else verifies the delivered snapshot again. The delivered patch and the report live in `<session>/final/`.
- Time is the only budget final verification draws on, so the reservation is time: the loop starts no turn when the remaining wall time is below 1.5 times the last verification (two minutes before the first). Steps and tokens never block final verification.
- A cancelled run is not verified (the user asked it to stop); its report is incomplete, bound to the snapshot, and says why.
- Verification installs dependencies from the lockfile where the repository has one the verifier can install from (npm, pnpm, yarn, bun, uv); without one, the workspace's tree is linked and the result says it is not reproducible.
- Instruction files are loaded from git's tracked list, so an untracked AGENTS.md in a working copy does not change what the agent is told; the budget is 24,000 bytes.
- Exit codes of `swarm run`: 0 complete, 1 a requirement failed, 4 incomplete with nothing failed, 5 blocked.

## 2026-10-31: automatic local use

- Discovery reads Ollama's `/api/version`, `/api/tags` and `/api/show` (OLLAMA_HOST honored) and, for an endpoint named with `--endpoint`, `/v1/models`. There is no provider registry: Ollama is discovered, and any other server is named.
- Ollama models are driven through `/api/chat`, not its OpenAI-compatible endpoint, because only the native API takes the context size (`num_ctx`) and turns thinking off; both report prompt and output token counts and durations apart.
- Excluded before any probe: entries with `remote_host` (the `:cloud` models), models without the `completion` capability or with `embedding`, a stated context below the configured one, and models whose metadata states no attention shape (block count, KV heads, key and value lengths), since their KV cache at the configured context cannot be estimated.
- Memory need is weights (the file size) plus a full 16-bit KV cache at the configured context plus 1 GiB of runtime overhead; the budget is total memory less a quarter, and never less than 8 GiB held back, for the OS, the docker VM and everything else.
- The readiness probe sends the agent's own system prompt and a repository-shaped prompt a quarter of the configured context long, at that context, and passes only on a reply that is exactly one bash block holding the requested command. Results are cached in `$SWARM_HOME/profiles/<host>.json` keyed by runtime, runtime version, endpoint, model, digest, quantization and context; any change re-probes. A profile from another machine (host name or total memory differs) is ignored.
- Selection probes eligible models strongest first and stops at the first ready one. With fewer than three finished tasks recorded per model, the choice is the largest ready model that fits, labelled a conservative default; with three or more, the best completion rate leads. An endpoint named with `--endpoint` is probed the same way, keyed by its address and served name since it states no digest.
- The default context is 32,768 tokens (`--context`), enough for the system prompt, instructions, a diff and several turns.
- Escalation happens at most once, to a ready model with more parameters, and only on `no-progress` or `unusable-replies` (four replies in a row that follow no reply form). A budget, a provider error or a blocked verification never escalates. With the largest model chosen by default there is nothing larger, so escalation applies when a smaller model was chosen by record or by name.
- Compaction is deterministic, never another model: past 60% of the context, turns between the first and the last six become a list of the commands run, their exit codes and output files, and the failed ones. Command output longer than a turn carries is written whole to `.swarm/outputs/<step>.txt` in the managed worktree and the turn names it. Three identical command-and-output turns in a row stop the loop as `no-progress`.
- No turn starts unless the remaining token allowance covers its estimated prompt and at least 256 output tokens; the completion cap of a turn is what remains after the prompt. Input and output are counted apart, with turns estimated from text counted separately.
- The run works in a detached git worktree under the system temporary directory, seeded with the user's staged, unstaged and untracked edits committed there as the run's base; `node_modules` and `.venv` are copied copy-on-write. The delivered patch is applied to the workspace with `git apply` (the index untouched) only when HEAD and the working tree are still exactly the starting state; `--no-apply` keeps the patch only. The worktree is removed at the end; session data stays.
- A `.venv` copied into the worktree still runs console scripts through the original environment's interpreter, and an editable install there points at the user's tree; the agent's own runs can therefore read the user's source for such a package. Verification is unaffected (it installs fresh in a container). Recorded in docs/known-issues.md.
- swarm.toml no longer pins a model; the evaluation names its own (`evaluationModel` in eval/run.mjs), so a fresh checkout runs with discovery.
- `swarm doctor --models` probes every eligible installed model and prints what each needs and whether it is ready; it is how a user (and this run) sees the readiness of every model.
- The managed worktree moved from the system temporary directory to a hidden directory beside the repository (`.<name>.swarm-<session>`), because a dependency named by a relative path (dossier's `file:../ironroot/packages/core-ts`, and the relative symlink npm makes for it) resolved from the temporary directory to nothing. ## 2026-11-01: which words of a command are paths

- Two redirect forms escaped the path check: a redirect written before the program (`> /tmp/x echo hi`) had its target dropped, and `>&/tmp/x`, which bash reads as both streams into that file, was read as a descriptor duplicate with the file left as the program's argument. Redirect targets are now kept apart from arguments and always offered to the guard, and `>|` and a redirect with no program beside it are unreadable.
- The shell reader decides which words are paths by program and position instead of offering every piece of every word. For sed, grep (egrep, fgrep), rg and awk an option table (`src/tools/argument-grammars.ts`) says which arguments are files, which are patterns or printed text, and which are a script; echo and printf open nothing; every other program has every word offered whole and in pieces, as before. Redirect targets are paths whatever the program. Of the 46 path refusals in the 2026-11-01 acceptance sessions (the ledgers named by `docs/acceptance/2026-10-31/`), 9 were text inside a sed script (20261101T013406-9a84a6 records 48 to 69, 20261101T092628-0b3280 records 78 and 113); `src/tools/quoted-path-denials.test.ts` replays them verbatim, and eight are allowed now while the ninth is refused on the `/tmp` file the same command writes. Removal condition: a table that proves wrong for a program is deleted, which returns that program to the old reading.
- An option table may leave out an option whose value is a number or a glob, because its value is then read as the first operand and the real first operand as a file, which only offers more. It may never list as valued an option that some implementation reads as a flag, and an option it does not list makes the whole command read as before. Where implementations differ (GNU tools read options after the first operand and BSD tools do not; BSD sed's `-i` takes the next word and GNU sed's takes nothing), every reading is ruled on, and a word is text only where all of them agree.
- A sed script is read for the files it names: `r`, `R`, `w`, `W` and the `w` flag of `s` offer exactly their file, and `e` or the `e` flag of `s` makes the command unreadable, which the old reader never caught. A script whose end GNU and BSD sed would find in different places (a delimiter inside brackets, `s/[/]/x/`), or that the reader cannot follow, is read as before, every piece offered; one such script among several `-e` scripts sends all of them back, because sed joins them into one program.
- An awk program is read the same way: a print to a string literal offers that file, and `system`, a pipe, `getline`, `ARGV`, a `@` directive or a computed print target make the command unreadable. This is stricter than before: `print > "/etc/x"` used to pass, because the piece offered was `"/etc/x"` with its quotes, a relative name inside the workspace.
- Four more of the 46 refusals named a relative path that a `cd` earlier in the command would have kept inside the workspace. That is a separate defect in the refusing direction, recorded in `docs/known-issues.md` rather than fixed here.
## 2026-11-01: context management

- Every turn's prompt is now the system prompt and repository instructions, then the task and the requirement record (byte for byte the same from turn to turn until the record changes, so a runtime's prompt cache can keep them), then the last four turns whole, then older turns as a bounded excerpt, then the working tree's status, its diff against the base (6,000 bytes at most) and the latest verifier findings, once, at the end.
